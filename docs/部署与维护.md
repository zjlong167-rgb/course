# 部署与维护

目标：192.192.99.188，Ubuntu22.04 amd64。项目独立根目录 /opt/course-platform；本次发布目录 releases/20261113，持久化 data/mysql、data/assets。默认80空闲；443属于其他应用，保留。对外HTTP IP访问，COOKIE_SECURE=false；没有配置或宣称TLS。后台账户使用独立随机密码，不能复用本地验收密码；凭据仅本机忽略文件 .local/production-admin.json 与服务器0600的 deploy/.env，私下交接。

## 构建和启动

运行时实际安装 Ubuntu docker.io29.1.3、Compose2.40.3。镜像版本：MySQL8.4.9、Alpine3.23.3、Nginx1.28.2-alpine；构建链Node24.13.0、Go1.26.1。锁文件保留。完整源代码构建入口 backend/Dockerfile、frontend/Dockerfile。远端DockerHub连接超时，因此本次在Windows编译Linux amd64 Go静态二进制和Vite静态文件，传输官方运行时镜像，按离线Dockerfile构建；不能将其描述成已通过远端完整多阶段源代码构建。

有网络环境：复制 deploy/.env.example 至 deploy/.env，填随机十六进制数据库密码（避免DSN/Compose插值字符）、独立管理员密码及绝对DATA_ROOT；新建 assets 并 chown10001:10001。进入deploy运行 `docker compose config --quiet`，`docker compose build`，`docker compose up -d --wait`。数据库不映射宿主端口；只有web映射80。迁移完成后启动API，再等健康启动web；已有用户不会被启动变量覆盖。

离线包：本机脚本 scripts/package-release.ps1 做npm ci、check、Linux编译、静态包及SHA256归档；输出.local，仅包含课程代码/样例和配置模板，不包含实际.env/口令/数据库。服务器解包后准备私有.env，导入经校验的官方运行时镜像，执行 `docker compose -f compose.yaml -f compose.offline.yaml build --pull=false api web`，再 `docker compose up -d --no-build --wait`。Compose运行方式相同，基础镜像须事先存在。初次部署实际过程证据见S09验收。

源码、构建产物与基础镜像归档随release保留；导出应用镜像可用 `docker save course-api:20261113 course-web:20261113 | gzip > application-images.tar.gz`，计算SHA256后异机保存。数据库和资源备份独立执行，不把应用镜像当数据备份。

## 健康、日志及日常操作

GET /api/health/live 进程存活；/api/health/ready连接数据库，失败503。Nginx同源代理/API，不缓存草稿。`docker compose ps`及 `docker compose logs --tail 100 api web mysql migrate` 检查；json日志每容器10MB×3轮转。不要运行config非quiet输出或inspect环境后将秘密写进报告。数据库与资源目录持续保留，常规停止用 `docker compose stop`，禁止用down -v清空数据。内存会话重启后需重新登录，单实例部署，不支持多API副本共享会话。

IP模式后续若需要TLS：可在独立入口端口/代理配置由用户提供的IP证书与私钥，Nginx启用ssl_certificate/ssl_certificate_key，改COOKIE_SECURE=true后重新建立会话，并检验HTTPS实际可达及cookie Secure。不要占用既有443；证书验证和续期须由维护人配置。本次没有TLS验收。

## 升级与应用回退

1. 新建独立releases/<新版本>，构建并保留旧应用镜像及.env访问权限，不覆盖旧文件。
2. 停唯一写入API并执行一致备份，记录当前release、备份SHA256和迁移版本。确认空间足够。
3. 相同COMPOSE_PROJECT_NAME与DATA_ROOT，使用新release的Compose，迁移先成功再启动api/web。校验ready、登录、目录、四课、历史及图片。
4. 仅当数据库结构与旧应用兼容时，将RELEASE指回保留的旧镜像并 `docker compose up -d --no-build api web`；不要自动运行down.sql。当前001/002迁移不可假定支持任意降级。
5. 数据库迁移失败涉及MySQL DDL隐式提交，保持API停止，检查schema_migrations及部分DDL；选择经审阅的修复迁移，或把升级前数据库+资源备份恢复到新的独立DATA_ROOT并验证后切换。数据回退会丢失备份之后写入，先另存现有数据并由负责人决定切换时间，不覆盖原目录。

## 一致备份与独立恢复

进入当前release的deploy，`sh backup.sh /opt/course-platform/backups/<唯一批次>`。脚本暂停唯一API写入进程，使用mysqldump single-transaction（InnoDB）并在同一停写窗口归档资源，复制compose及manifest，生成SHA256SUMS后恢复API。不能有绕过API的直接DB写入或其他API副本；若有，先统一停写。备份包含用户hash与课程资料，应权限0700目录、0600文件，离机加密副本由维护者管理；本次不虚构已配置异地定时备份。

恢复必须在另一deploy目录准备独立.env：不同COMPOSE_PROJECT_NAME、全新绝对DATA_ROOT、不同HTTP_PORT（本次18082）、HTTP_BIND=127.0.0.1。复制部署脚本与Compose，执行 `sh restore.sh <备份目录>`。脚本验证全部SHA256，拒绝course-prod、80端口及已存在目录；解包资源并校正UID，启动独立MySQL并导入SQL，再启动迁移/API/web。原数据库与资源不会被覆盖。

导入SQL并不代表恢复通过。按S09恢复检查登录、目录快照/版本ID、所有历史正文、当前及历史资源哈希、四类播放器控制/讲解/详情与图片。只在验证完毕后人工决定是否切换正式入口。恢复演练保持localhost:18082，仅通过SSH隧道测试，避免公开第二个副本。演练容器可stop保留数据；清理前核对项目名和绝对目录，不能误删生产数据。

官方操作依据：[Docker Ubuntu安装](https://docs.docker.com/engine/install/ubuntu/)、[MySQL mysqldump](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)。

最终交付补充：独立打包与包内镜像构建已实跑通过，使用COPY --chmod=755保证Windows生成的Linux二进制权限。部署包和源码包及SHA256在目标release目录。恢复演练数据保留，交付时停止course-restore容器以释放内存；需复核时在restore-20261113目录执行docker compose up -d --wait并建立SSH隧道。
